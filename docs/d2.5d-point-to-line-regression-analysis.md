## EXECUTIVE FINDING

D2.5d's geometric constraint model is substantially sound, but its interaction and annotation implementation conflated three different concepts:

1. the infinite selected line's **tangent**;
2. its **normal**, which is the measured point-to-line direction; and
3. an annotation's freely chosen **placement**.

The measurement correctly uses the perpendicular distance to the infinite line. The renderer then deliberately builds the arrow/value segment along the tangent, producing the opposite visual orientation. Separately, D2.5d changed placement preview state from lightweight references plus a live cursor to a materialized `DrawingDimension`. The legacy single-line pointer-move branch updates only dimension kind and leaves that materialized dimension's offset frozen at the line-selection click. Finally, line-first selection is not represented as “one reference acquired”: selecting a line immediately enters legacy line-dimension placement. A click-time conversion heuristic tries to reinterpret the next point click as point-to-line. During that state preselection is suppressed, and at an Origin coincident with a line endpoint the endpoint priority tier wins, so a datum reference is never constructed.

These are real defects, but they are concentrated in the interaction/placement and annotation layers. The Point + Line discriminated representation, rank equation, component membership, and movement-preference solver path do not need rollback.

## ISSUE A — POINT-TO-LINE ANNOTATION

### Intended geometry

For point `P` and infinite line through `A` and `B`, let unit tangent `u = (B-A)/|B-A|` and a perpendicular unit normal `n = (-u.y, u.x)`. The foot is `Q = A + dot(P-A,u)u`. The measured scalar is `|dot(P-Q,n)|`.

The main dimension segment, arrows, and value must run from the point side toward the line side along `n` (or `-n`), hence perpendicular to the selected line. Any displacement needed to place the annotation should shift/support that normal segment without changing its measured direction; line-side witness geometry may run parallel to `u` to reach the chosen placement.

### Current geometry

The scalar measurement is correct: `measurePointToLine` evaluates the normalized cross-product magnitude and therefore measures distance to the infinite line, not distance to the finite segment.

The annotation code also correctly computes `u` and the unbounded projection parameter, then constructs `Q`. It then switches to the wrong basis:

- `ox, oy` use normal `n` multiplied by `placement.offset`;
- `center = Q + offset*n` moves the annotation center normal to the selected line;
- `a = center - half*u` and `b = center + half*u` make the main arrow/value segment tangent to the selected line;
- `half` is half the measured point-to-line value, so the correct scalar is incorrectly used as the length of a tangent segment;
- generic rendering places arrow markers on `a -> b` and derives `textAngle` from `b-a`, so both arrows and text inherit the tangent orientation;
- generic extensions join `sourceA=Q` to `a` and `sourceB=P` to `b`; these diagonal legs are not a deliberate line-parallel witness construction.

The source comment explicitly says the main value line is “deliberately parallel,” confirming that this was an implementation choice rather than a numerical projection accident.

### Exact root cause and code path

1. `createPointToLineDimension` stores placement with `dimensionOffset(line, cursor, 'ALIGNED_DISTANCE')`. That function projects cursor-minus-line-midpoint onto the **normal**. This is inherited aligned-line placement semantics, not a point-to-line-specific placement model.
2. `DrawingWorkspace.annotationGeometry` computes the infinite-line foot correctly using tangent projection.
3. The same function uses the stored scalar as a normal translation of the center, then uses the tangent `u` for arrow endpoints. This is the orientation inversion.
4. The shared SVG renderer places markers on those endpoints and computes `rawAngle`/`textAngle` from them, propagating the wrong tangent direction to the value.

### Local or architectural?

The measurement/constraint architecture is sound. The visual repair is localized in effect, but should not be a one-line `u`/`n` swap: point-to-line needs an explicit derived annotation-geometry strategy that defines the perpendicular arrow endpoints and parallel witness segments from point, foot, and placement. That strategy can still feed the common SVG primitives.

## ISSUE B — SINGLE-LINE PLACEMENT REGRESSION

### Accepted D2.5c1c behavior

D2.5c1c stored `{references, cursor, kind}` in `placementPreview`. Pointer movement continuously replaced `cursor` and potentially `kind`. On every render, `previewDimension` was recreated with `createPointToPointDimension(..., cursor, ...)`, which recomputed `placement.offset` from the current cursor. A single line was represented by its two endpoint references, so its preview followed the cursor freely normal to the selected dimension line.

### Current D2.5d behavior

D2.5d stores a fully materialized preview `dimension` plus `cursor`. A first line click calls `createLineDimension` immediately, freezing the initial offset at the hit point—normally close to the line. During pointer movement:

- point-to-line previews update their placement offset;
- all other previews update only `kind`;
- legacy line and point-to-point preview placement is therefore stale.

The eventual placement click recomputes the committed offset, so stored post-click geometry can land at the click. However, the user does not receive the accepted live free-placement preview, and the click-time conversion heuristic can consume clicks near point candidates. This explains why creation feels constrained while later annotation drag still works: the drag path separately recomputes `dimensionOffset` on every move.

### Exact root cause and files/functions

- `drawingDimension.ts` changed `DimensionToolState.placementPreview` from references/cursor/kind to a materialized `DrawingDimension`/cursor.
- `DrawingWorkspace.handlePointerDown` materializes a single-line preview at the selection click via `createLineDimension`.
- `DrawingWorkspace.handlePointerMove` special-cases `POINT_TO_LINE_DISTANCE` placement updates, but its `else` branch changes only `kind`. It does not call `createLineDimension`/`createPointToPointDimension` again and does not update `placement.offset`.
- `previewDimension` now aliases the stored object instead of being derived from the live cursor.
- `dimensionOffset` itself did not introduce the regression; it still supports free normal offset. The regression is that the legacy preview stopped invoking it as the cursor moves.
- The commit path recomputes offset and annotation drag remains live, which is why the defect is isolated to creation preview rather than persisted placement or drag.

### D2.5d behavior to restore

Restore D2.5c1c's invariant for non-point-to-line dimensions: preview geometry and offset are derived from current references, current interpretation kind, and current cursor on every pointer move/render. Do not route legacy single-line placement through point-to-line selection/conversion logic. Keeping a materialized preview object is possible, but then every legacy move must update its derived placement; retaining a distinct preview intent and deriving the object is cleaner.

## ISSUE C — LINE -> ORIGIN SELECTION

### Exact interaction state

After a line-body first click, D2.5d does **not** enter `acquiringReference` with an entity reference. It enters `placementPreview` containing a legacy endpoint-to-endpoint line dimension. Therefore the normal second-reference state machine—whose `first.kind === 'entity' && reference.kind !== 'entity'` branch correctly supports datum and SketchPoint references—is unreachable for line-first input.

Instead, the placement handler detects that the preview consists of two legacy endpoint references to one line and opportunistically converts a point/origin hit into point-to-line. This mixes legacy placement and second-target acquisition in one click path.

### Exact reason Origin is excluded

There are two cooperating interaction defects:

1. `handlePointerMove` returns early for every `placementPreview`, before the general dimension-preselection update. Thus no point or Origin becomes visibly preselected after the first line; the UI advertises placement rather than second-target acquisition.
2. `collectDimensionReferenceCandidates` puts all line endpoints and Origin in the same sorted tier, but constructs the array as `[...points, ...origin]`. With equal distance—most importantly when the selected line endpoint/shared SketchPoint is at `(0,0)`—stable sorting leaves the endpoint before Origin. `resolveDimensionPreselection` returns only the first candidate, `resolveDimensionCandidate` converts it to a `sketchPoint`, and `preselectionReference` never constructs `{kind:'datum', datum:'ORIGIN'}`. The click-time conversion consequently creates a zero-distance point-to-its-own-line relation (or fails as a duplicate) rather than Line -> Origin.

Origin is therefore not globally absent from candidate collection and is not excluded because datum references are unsupported. It is shadowed by endpoint priority at coincident geometry, made opaque by the wrong post-line state, and there is no target-aware filtering/selection rule to choose the fixed datum.

### Is ordinary Line -> Point affected?

Ordinary line endpoint/shared SketchPoint hits are accepted by the click-time conversion, so the exact Origin-shadowing failure does not block them. Nevertheless they use the same structurally wrong `placementPreview` conversion path, lack second-target preselection feedback, and cannot be treated robustly as a deliberate second-reference acquisition. A line's own endpoint is also accepted even though it yields a degenerate zero-distance relationship. Tests should cover ordinary independent points, shared points, own endpoints, and Origin distinctly.

## SEMANTIC MODEL REVIEW

`POINT_TO_LINE_DISTANCE` is reusable and expresses the intended identity well:

- it is a discriminated dimension kind;
- references are canonically `[DrawingPointReference, DrawingEntityReference]`, independent of click order;
- `movementPreference` records click-order solver intent separately from identity;
- Origin already resolves as a fixed point datum;
- canonical duplicate identity is Point + Line, while movement preference is intentionally excluded;
- reference dimensions recompute their displayed measurement from current geometry.

The model should remain. Placement is currently a generic scalar whose meaning is overloaded, but that is an annotation-placement concern, not evidence against the semantic reference model.

## RANK / DOF REVIEW

The integration is reusable:

- a point-to-line equation connects the point plus both authoritative line endpoints in one component;
- the Origin key participates in equations but is omitted from variable columns;
- the Jacobian includes derivatives for point and both endpoints, so line translation and rotation are represented;
- one driving point-to-line distance contributes one scalar row, and rank is determined numerically rather than assumed;
- direct manipulation and visual-state dependency collection recognize entity references as touching both line endpoints.

No evidence links the browser defects to rank/DOF. The finite-difference gradient is a maintainability/performance tradeoff and zero-distance uses a deterministic one-sided convention, but neither requires redesign for the reported regressions.

## SOLVER REVIEW

The component solver integration is reusable. It evaluates the same perpendicular-distance function used for measurement, includes the three involved point keys, verifies all component equations, and chooses preferred variables from `movementPreference`:

- preference `point` moves only the point when it is not Origin;
- preference `line` moves the line endpoints;
- Point -> Line with Origin necessarily falls back to line-side variables because Origin is excluded;
- if the preferred subset cannot solve the connected component, the established fallback permits all component points.

The D2.5d test demonstrates both preference directions, fixed point behavior for line preference, fixed line behavior for point preference, shared-point topology retention, and post-solve verification. The broad solver refactor is terse and deserves ordinary regression scrutiny, but there is no evidence that it causes Issues A–C or contains an architectural shortcut requiring rollback.

## PLACEMENT ARCHITECTURE REVIEW

Legacy line/point-to-point and point-to-line dimensions should share a common interaction shell—activate, acquire semantic references, preview, commit, cancel—but should use separate derived placement/annotation strategies.

- **Legacy dimension strategy:** retain D2.5c1c behavior: choose horizontal/vertical/aligned interpretation and calculate offset from the live cursor relative to the endpoint pair.
- **Point-to-line strategy:** derive infinite-line foot, tangent, signed normal, perpendicular arrow/value endpoints, and line-parallel witness displacement from its own placement intent.
- **Common shell:** store acquisition intent and cursor, dispatch by semantic relationship, and materialize the preview consistently. Do not infer “line-first second target” by inspecting whether a legacy dimension happens to contain two endpoint references from one entity.

The current click-time reinterpretation is the entanglement to remove. This is a focused interaction rewrite, not a reason to discard the semantic/solver implementation.

**CLASSIFICATION: REWRITE MORE CLEANLY**

The Point-to-Line annotation branch deliberately uses tangent endpoints; the preview move branch freezes legacy placement; and line-first acquisition is simulated through a click-time conversion of a legacy line preview. Rewrite those localized interaction/annotation portions around explicit acquisition and per-kind derived geometry. Preserve unrelated accepted workspace behavior.

**CLASSIFICATION: FIX**

Clarify/separate point-to-line placement derivation instead of calling legacy `dimensionOffset(..., 'ALIGNED_DISTANCE')`, and support a preview intent that does not freeze legacy offsets. Candidate resolution also needs context-aware handling so Origin can win as an intentional datum when coincident with an endpoint.

## MISSING TEST COVERAGE

Existing tests passed because the new suite imports pure geometry, model, rank, and solver functions only. It never renders `DrawingWorkspace`, drives its pointer state machine, inspects preview geometry, or asserts SVG line/text orientation. Its reverse-intent check constructs dimensions directly; it does not reproduce reverse-order browser selection.

Required coverage:

1. **Single-Line Dimension initial free placement.** Select a line body, move through multiple normal offsets before committing, and assert that preview arrow/value/witness geometry follows each cursor position and that commit matches the final preview. Include horizontal, vertical, and oblique lines and interpretation hysteresis.
2. **Point-to-Line main arrow orientation.** For horizontal, vertical, and oblique lines, assert `dot(mainSegment, lineTangent) ~= 0`, the main-segment magnitude/direction represents perpendicular distance, and arrow markers are attached to that segment.
3. **Point-to-Line text orientation.** Assert the text angle derives from the perpendicular main segment, normalized only for readability; for a horizontal selected line the value is aligned vertically (subject to the established upright policy), not horizontally.
4. **Line -> ordinary Point second selection.** Drive real pointer events: after a line first click, verify the state requests a point, an independent SketchPoint/endpoint can preselect and become the canonical first point reference, and movement preference is `line`.
5. **Line -> Origin second selection.** Cover both an unobstructed Origin and Origin coincident with a line/shared endpoint. Assert the second reference is the datum, Origin gets selection feedback, the stored canonical pair is Origin + Line, and movement preference is `line`.
6. **Point -> Line.** Verify point acquisition, line-body preselection, canonical Point + Line references, movement preference `point`, preview geometry, and commit.
7. **Origin -> Line.** Verify Origin acquisition and feedback, line-body second selection, fixed Origin reference, canonical identity, line movement on edit (because Origin cannot move), and perpendicular annotation.
8. **Reverse selection behavior.** Compare Point -> Line with Line -> Point: same canonical identity/duplicate key and measurement, different movement preference only. Repeat with Origin and verify fixed-datum override.
9. **Annotation drag after creation.** Drag legacy and point-to-line annotations at multiple zoom levels. Assert geometry follows the pointer, semantic references/value/preference remain unchanged, final offset equals preview, and undo/redo remains one transaction.

Add lower-level candidate tests for coincident endpoint/Origin priority and a workspace-state test proving `placementPreview` does not suppress target feedback when another target is still required.

## RECOMMENDATION

**STRATEGY A — REPAIR D2.5d**

Repair is cleaner than rollback/reimplementation because the reusable majority is in the hard semantic and numerical layers: typed Point + Line identity, duplicate classification, infinite-line measurement, rank/DOF equation, component membership, movement preference, direct-manipulation validation, and solver verification. The three observed failures trace to a small, identifiable surface: `DrawingWorkspace` acquisition/preview/annotation logic plus placement/candidate helpers in `drawingDimension.ts`.

This should not become “patch on patch.” The repair should remove—not extend—the line-preview reinterpretation heuristic, restore the accepted legacy placement strategy, and introduce one explicit point-to-line annotation strategy. Rolling back all of D2.5d would discard sound and tested solver/rank work only to recreate it.

## PROPOSED NEXT MILESTONE

The smallest clean milestone is an interaction-and-annotation corrective release with no solver/rank/type redesign:

1. restore D2.5c1c live placement derivation for every legacy single-line and point-to-point preview;
2. represent line-first as explicit first-reference acquisition, with Point/SketchPoint/Origin as second-target candidates and deterministic datum handling at coincidence;
3. replace point-to-line annotation derivation with perpendicular main arrow/value geometry and line-parallel witness geometry;
4. keep the persisted semantic dimension and movement preference unchanged;
5. add the nine browser/state/geometry regressions listed above before browser acceptance.

No implementation code is included in this report.
