## EXECUTIVE SUMMARY

The two symptoms are **separate defects with a shared conceptual boundary, not one state-machine bug**.

1. **Third green:** there is no fourth permanent stroke value or fourth semantic state in the current committed-Line render path. Each rendered Line gets exactly one of `geometry-free`, `geometry-constrained`, or `geometry-fully-locked`, mapping to `#33C757`, `#137A3E`, and `#111827`. Temporary preselection/drag changes the stroke to cyan, not green. The only remaining persistent presentation difference between two same-state green Lines is selection's larger width (`2.2` versus `1.8`), whose extra antialiased/covered pixels can make the same green look darker or more saturated. Exact coincidence/duplicate entities can likewise overdraw, but the application neither generates a second render copy for one ID nor rejects geometrically duplicate IDs. Thus the code definitively rules out a legitimate third green and a CSS color-cascade source; absent the reported browser DOM/screenshot, the exact observed instance can only be classified as **D, presentation by width/antialiasing or coincident overdraw**, with persistent selected width the confirmed normal path and duplicate geometry a data-dependent possibility.
2. **Visual semantics:** Line classification is a hybrid. `CONSTRAINED` is an **endpoint-incidence** test: any Driving dimension reference resolving to either endpoint (including an entity reference to another Line sharing that point) marks the Line constrained. `FULLY_LOCKED` then uses zero DOF of every constraint-equation component containing the Line's endpoints. It is not a per-Line null-space/mobility analysis. This makes adjacent `BC` dark green for `|AB|=L` solely because it shares `B`.
3. **Drag freeze:** Direct Manipulation never invokes the component solver. It translates exactly the selected point, or exactly both selected-Line endpoints, then validates affected Driving measurements and rejects the candidate if any changes by more than `1e-7 mm`. For a length-constrained endpoint, an ordinary Cartesian pointer delta almost never lands exactly on the constraint circle, so valid tangential/rotational mobility is effectively inaccessible. This is primarily **D + E: direct candidate rejection because the solver is not invoked**. Affected-constraint scoping and shared-point ownership correctly explain which equation is checked, but do not create a false equation.
4. **Relationship:** both areas need mathematically explicit geometry freedom, but they must remain separate consumers: visual classification answers what freedoms an entity has; dragging solves a user objective on the component constraint manifold. Sharing Jacobian/component/null-space infrastructure is appropriate. Sharing a single UI state machine is not.

## BROWSER SYMPTOMS

### Third Sketch green

The report of three green appearances plus black is compatible with two actual permanent green values plus a thicker selected instance of either green. A click leaves `selectedGeometry` persistent; the selected Line remains `2.2` px wide until selection changes. A meaningful successful drag clears selection, but an invalid/frozen drag retains the last valid candidate and can leave the selected state in place until pointer-up logic clears it after threshold crossing. No normal state class changes selected geometry to another green.

### Partially constrained geometry unable to move

The interaction accepts only the raw target subset translated by the full pointer delta. It does not calculate a compatible displacement. Therefore a length-only endpoint has a mathematically one-dimensional instantaneous tangent direction relative to its fixed counterpart, but a finite straight mouse delta changes length except for the special chord solutions that land exactly back on the circle. Visually, the preview remains at the last valid document, which normally looks frozen.

## CURRENT VISUAL STATE ARCHITECTURE

The authoritative chain is:

1. `DrawingWorkspace` resolves each ID in `entityOrder` once and emits one SVG `<line>` in `.drawing-sketch-geometry`.
2. It calls `getGeometryConstraintVisualState` twice per render (for `data-constraint-state` and the class), with no freedom proof.
3. `geometryConstraintVisualClass` maps the result to exactly one class: `geometry-free`, `geometry-constrained`, or `geometry-fully-locked`.
4. Base CSS gives `.drawing-line-entity` width `1.8`; the three state selectors supply the permanent stroke.
5. Later, equal-specificity temporary selectors override stroke in stylesheet order: `is-dimension-preselected` and `is-geometry-preselected`/`is-geometry-dragging` all use cyan `--drawing-hover`. `is-geometry-selected` changes only width to `2.2`.

Legal class combinations are one and only one permanent state plus any interaction classes whose React conditions happen to coincide:

- `geometry-{free|constrained|fully-locked}`: mutually exclusive.
- `is-dimension-preselected`: line under the Dimension cursor or the first selected Line target; it can coexist with a permanent state.
- `is-geometry-preselected`: line under Select hover; it can coexist with selection and drag transiently.
- `is-geometry-selected`: persistent selected Line; may coexist with preselection and active drag.
- `is-geometry-dragging`: active Line target only; may coexist with selected and preselected.
- There is no Line class named plain `is-selected`, plain `is-preselected`, or `is-dragging`, and no further tool-specific Line class.

Cascade result: preselection/drag cyan wins over the permanent stroke because those rules occur later and have equal specificity. Selection changes width only. The containing sketch group has no opacity, filter, color, blend mode, or stroke. The SVG/root tool classes affect cursors only. Permanent Lines have no opacity/filter/blend mode. Dimension witnesses are in a later sibling layer, use `currentColor` green at opacity `0.72`, and can physically cross or coincide with a sketch Line, but do not inherit into it.

## THIRD GREEN ROOT CAUSE

**Firm code classification:** not A (fourth permanent state), not B (green transient state), not C (unexpected cascade), not F (tool-specific green), and not G (a third state-class value). The repository exposes exactly two green permanent strokes and black.

The remaining confirmed presentation mechanism is **D: width/antialiasing/overdraw**:

- persistent selected width is `2.2` rather than `1.8`, while retaining the same computed green;
- SVG rasterization and background-grid coverage make equal RGB strokes of different width appear different;
- a later dimension witness can add translucent green pixels where it overlaps geometry;
- distinct Line entities with coincident coordinates are rendered independently and can overdraw.

The normal drawing path preserves unique entity IDs and emits one element per `entityOrder` entry. `appendEntityToActiveSketch` refuses an already-used ID, but intentionally does **not** test geometric coincidence. Migration creates one entity per legacy entity and independent endpoint identities; it neither duplicates one entity nor merges coincident legacy Lines. Topology validation catches missing points, repeated endpoints, and orphan points, but not duplicate IDs in `entityOrder` or coincident geometry. Consequently duplicate/coincident geometry is possible from persisted or deliberately created input, not demonstrated as an automatic result of ordinary connected Line creation.

Because no screenshot/DOM snapshot accompanied this repository task, static code can identify the set of possible causes but cannot prove whether the particular browser pixels came from selected width, a coincident entity, or a dimension witness. The strongest supported diagnosis is **selected-width perceptual variation**, with DOM inspection (`class`, computed `stroke`, `stroke-width`, and same-coordinate siblings) required to distinguish the data-dependent alternatives in that exact session.

## CURRENT CONSTRAINT ANALYSIS

### Variables and equations

Every authoritative SketchPoint contributes two columns, `x` and `y`. The immutable Origin is a constant coordinate and contributes no columns. Each supported Driving dimension contributes one scalar row:

- aligned/point-to-point length: unit direction gradient;
- horizontal distance: an x-only gradient;
- vertical distance: a y-only gradient;
- point-to-line distance: a six-column finite-difference gradient;
- line-to-line distance: an eight-column finite-difference gradient.

`LINE_TO_LINE_ANGLE` currently returns no constraint equation and is rejected by Dimension edit; it therefore does not reduce analyzed rank. This is an explicit present limitation, not a future-ready angle constraint implementation.

Only `role === 'driving'` enters analysis. Reference dimensions contribute neither union edges nor Jacobian rows and do not reduce DOF.

### Components

The analysis components are **constraint-incidence components**, not full Line-topology components. Union-find connects non-datum points that co-occur in a Driving equation. A geometrical Line by itself does not connect its endpoints in this graph unless an equation mentions both. Every point still gets a component, so unconstrained points are singleton components with two variables and zero rank.

For each component:

`component DOF = 2 * number of SketchPoints - rank(J)`.

Rank uses elimination with absolute `1e-10` and relative `1e-9` tolerance. `componentByPointId` then maps every point to its component. `drawingConstraintDegreesOfFreedomForPoints` is a separate local-column rank helper used in Dimension-edit movement ownership; Direct Manipulation does not use it.

### Datum caveat

A point-to-Origin dimension places the point's two coordinates in the variable set but Origin in no variable set. One independent distance equation removes one scalar DOF. Two suitably independent datum equations can fix both coordinates. The Origin itself is never movable. A future Fixed constraint should similarly add two independent scalar equations (or eliminate both variables), rather than being represented as shared topology.

## CURRENT LINE VISUAL STATE SEMANTICS

With the Workspace's actual no-proof call:

- **FREE:** no Driving dimension has any reference that resolves to either endpoint of the Line. This is incidence, not “all endpoint motions are unconstrained.”
- **CONSTRAINED:** at least one such Driving reference exists, and at least one endpoint's constraint component has nonzero DOF.
- **FULLY_LOCKED:** at least one Driving reference exists and every constraint component looked up for both endpoints has zero component DOF.

An optional external rigorous zero-DOF proof could force `FULLY_LOCKED`, but no Workspace caller supplies one. The current meaning is closest to **B only as a coarse incidence approximation**, followed by component zero-DOF for lock. It is not A (“any constraint anywhere in a topologically connected component”), and it is not C/D (a computed loss of the Line's own shape/pose mobility).

The nomenclature also differs: code says `FULLY_LOCKED`, while the visual contract says “FULLY CONSTRAINED.” They represent the same black presentation state in this audit.

## PER-ENTITY VS COMPONENT STATE

Current Line state is not purely component-based; it is **incidence-gated, component-DOF-finished**. Nevertheless, shared endpoint identity propagates incidence:

- If an `AB` endpoint reference resolves to shared point `B`, target Line `BC` includes `B`; therefore `hasDrivingRestriction(BC)` is true.
- `BC` becomes `CONSTRAINED` even though moving `C` cannot affect `|AB|`.
- It becomes `FULLY_LOCKED` only if the components of both `B` and `C` report zero DOF. Since an unconstrained `C` is normally its own two-DOF singleton, this particular example remains merely constrained.

So, “one equation anywhere in a Line-topology component makes every Line constrained” is too broad. The exact rule is “one equation incident to a shared endpoint makes every Line incident to that point constrained”; propagation does not recursively cross unconstrained `BC` to a further point/Line.

## REFERENCE CASE A-B-C

For three distinct, noncoincident points with variables

`q = (Ax, Ay, Bx, By, Cx, Cy)`, there are **6 variables**. The one equation is

`f(q) = ||B-A|| - L = 0`.

At nonzero length its Jacobian is

`J = (-ux, -uy, ux, uy, 0, 0)`, where `u=(B-A)/L`.

Thus there is **1 independent equation, rank 1, and 5 component/topology DOF** in the mathematical mechanism. The implementation's constraint graph reports `{A,B}` as a four-variable component of rank 1 and DOF 3, plus `{C}` as a singleton component of DOF 2; their sum is the same 5. Shared Line topology does not add an equation.

### Point-level freedom

The admissible infinitesimal motions satisfy

`u · (dB-dA) = 0`.

- `A` can move in any requested direction if `B` is allowed to respond appropriately.
- `B` can move in any requested direction if `A` is allowed to respond appropriately.
- If `A` is held fixed, `B` has one tangential infinitesimal DOF (and exactly moves on the radius-`L` circle at finite scale).
- `C` has two completely independent DOF.

### Line AB freedom

AB has three rigid pose DOF before constraint (two translations, one rotation) plus one length/shape scalar in endpoint coordinates. Fixing length removes only that shape scalar, leaving **3 Line mobility modes**: two translations and one rotation. It is not fully constrained.

### Line BC freedom

BC has unconstrained endpoint `C` and a shared `B` that remains mobile on the global solution manifold. Its position, orientation, and length can all change. The AB equation can couple a chosen motion of `B` to `A`, but it removes no freedom from `C` and does not fully constrain BC.

## EXPECTED CAD MOBILITY

All of the following are legitimate:

- **Global translation:** add the same 2-vector to A, B, and optionally C; AB length is unchanged.
- **Global rotation:** rotate the entire chain about any center; AB length is unchanged.
- **Movement of C:** arbitrary 2D movement, deforming BC without touching AB.
- **Movement of B:** arbitrary target movement is possible if A may move with it; with A held, B is restricted to the circle about A.
- **Rotate AB around A:** move B on its circle; BC follows at B while C may stay or move.
- **Rotate AB around B:** move A on its circle; BC need not change.
- **Translate AB with BC following at B:** translate A and B equally; leave C fixed (deforming BC) or translate C too.
- **Deform BC through C:** arbitrary C movement.

The expected statements in the prompt are mathematically correct: AB's length is fixed while orientation and position remain free; BC retains substantial freedom; B participates in an equation but is not immobile.

## CURRENT DIRECT MANIPULATION ARCHITECTURE

1. In Select mode, pointer-down runs the shared finite-geometry hit resolver. Endpoint hits are converted to the authoritative shared point ID; Line hits retain the Line ID.
2. Pointer capture begins a drag session containing the target, pointer/model start, immutable start document, current candidate, and threshold flag. There is no DOF gate at pointer-down.
3. After 4 screen pixels, each preview is recomputed from the drag-start document and total delta.
4. Point target moved set = exactly that point. Line target moved set = exactly its two unique endpoints. Neighboring endpoints/Lines are not recursively collected, though shared IDs naturally move every incident Line endpoint.
5. A candidate translates every moved point by the identical delta.
6. “Affected Driving dimensions” are selected from the **start document** by direct reference incidence with any moved point. Entity references expand to that entity's two point IDs. References are excluded.
7. Candidate measurements are compared with stored values at `1e-7 mm`. Invalid candidate returns `null`; Workspace retains the previous valid candidate.
8. Pointer-up commits the final candidate through `transactDrawingDocument` once. Escape cancels. A no-op has no History entry.

There is no rank gate, FULLY_LOCKED gate, snap/inference, component expansion, null-space projection, or solver invocation in this path.

## POINT DRAG

- **Isolated FREE:** arbitrary translation of the point succeeds.
- **Isolated length-constrained endpoint:** raw delta succeeds only if the other endpoint remains fixed and the finite endpoint happens to land back at exactly the target radius. Tangential infinitesimal intent is not integrated along the circle; typical movement rejects and appears frozen.
- **Horizontal-distance endpoint:** y-only motion succeeds; any x component changing `|dx|` rejects.
- **Vertical-distance endpoint:** x-only motion succeeds; any y component changing `|dy|` rejects.
- **Connected constrained:** only the selected shared point moves. The solver cannot move another point to accommodate it, so any directly affected measurement change rejects. Moving C in the reference chain succeeds because C is not referenced by `|AB|`.
- **True zero-DOF:** all nonzero moves that alter an affected measurement reject, but there is no explicit zero-DOF check. Redundant or unsupported constraints could expose edge behavior; immobility is an emergent validation result rather than a rigorous eligibility decision.

## LINE DRAG

- **Isolated FREE:** both endpoints translate equally; succeeds.
- **Isolated length/horizontal/vertical constrained:** equal translation preserves endpoint differences and succeeds. Thus the current implementation already permits the important rigid translation of AB.
- **Connected constrained:** both selected-Line endpoint IDs translate. Shared points drag adjacent Lines at the joint, but the adjacent Line's other endpoint does not follow. If any affected dimension uses only the selected Line's two endpoints, rigid translation preserves it. If a constraint relates a shared endpoint to geometry not equally translated, it rejects. No solver moves the rest of the component.
- **True zero-DOF:** ordinary Line translation should reject through affected measurements, but again there is no explicit rank eligibility gate.

For `A-B-C, |AB|=100` specifically:

- drag C: succeeds freely;
- drag B: generally rejects because A remains fixed and length changes; exact finite points on the circle succeed;
- drag BC: B and C translate; generally rejects because A stays fixed, even though a solver could translate A too or project B's movement;
- drag AB: A and B translate equally and succeeds; C stays fixed, so BC deforms.

## CONSTRAINT-SCOPED DRAG

Scoping is direct moved-point incidence, not full component incidence. Sharing B correctly causes a BC Line drag to include AB's length dimension because BC moves B. This is not intrinsically wrong: the proposed raw translation of B really does affect `|AB|` while A is stationary. The architectural shortfall is that “affected” means “must remain numerically unchanged by this exact candidate,” rather than “include this equation in a solve that may move other authorized points.”

A drag of C alone selects no AB dimension and succeeds. A drag of a wholly unrelated Line ignores even a stale invalid AB equation, which is the intended D2.5b4b improvement and should be retained.

## SOLVER USAGE

Direct Manipulation uses **model A**: direct candidate followed by rejection. It imports only the solver tolerance, not `solveDrawingDimensionEdit` or its component solver.

Dimension edit uses a damped normal-equation component solver and specialized rigid translations. It builds the Driving-equation component, chooses variable ownership/preferences, holds non-variable coordinates as anchors, retries broader variable sets for ordinary dimensions, verifies all relevant residuals, and commits solved geometry with the edited value. It has hard anchoring by omission and deterministic ownership, but no general weak-stay system or user edit-target objective.

## DRAG ROOT CAUSE

**Primary classification: D + E.** Direct candidate rejection blocks motion because the component solver is not invoked. Confirmed contributing mechanics are:

- **B:** moved-point construction is deliberately narrow (one point or the two Line endpoints), so other points cannot respond;
- **C/H:** stable shared-point scoping correctly brings a neighboring equation into validation;
- **not A:** there is no early visual/DOF UI gate;
- **not F:** Direct Manipulation creates no solver anchors because it never calls the solver;
- **not G:** rank/visual state is not consulted by dragging.

Consequently Problem B is not caused by Line color classification. Both expose the need to distinguish incidence from admissible mobility, but their current codepaths are independent.

## NULL-SPACE / DOF OPTIONS

1. **Constraint incidence.** Cheap and explainable; handles references/Driving separation. It overcolors shared neighbors and cannot distinguish which attribute or motion is lost. Suitable as a conservative badge, not authoritative per-Line DOF.
2. **Local Jacobian columns/rank contribution.** Reveals whether equations have sensitivity to endpoint variables. Column nonzeros alone still confuse coupling with loss; rank must be compared against an entity motion map.
3. **Null-space projection.** Compute a basis `N` for `null(J)` and project endpoint observables/motion generators through it. It answers whether admissible `dq=N z` can change midpoint translation, angle, length, or individual endpoints. This is the most direct infinitesimal definition, but singular/degenerate poses and finite moves require care.
4. **Counterfactual rank.** Remove constraints incident to the entity and compare ranks or observable mobility. Useful for attribution (“which constraints reduced freedom”), but shared/multi-entity equations make ownership policy-dependent and repeated factorization expensive.
5. **Entity mobility test.** Ask whether any null-space vector moves either endpoint. Excellent for FULLY CONSTRAINED eligibility but too coarse for FREE versus partial: a fixed-length Line remains mobile.
6. **Separate shape versus pose.** Map null-space to differential observables: length `dℓ`, orientation `dθ`, and midpoint `dmx,dmy` (with endpoint mobility as a fallback). This gives truthful user semantics across constraint kinds. Translations/orientation are not globally independent in connected topology, so report mobility dimensions/rank rather than simple booleans where needed.

Recommended core: cached component Jacobian factorization/null-space plus an entity observable projection, supplemented by incidence attribution. For a Line with endpoint extraction matrix `E`, compute the attainable entity motion space `range(E N)`. Compare it with the corresponding topology-only baseline, and project into stable shape/pose observables. For finite drag, solve constraints plus a temporary target objective rather than directly applying `N` over a long delta.

## RECOMMENDED LINE STATE SEMANTICS

Use a counterfactual, entity-observable definition rather than mere component membership:

- Let `M_e` be the space of admissible infinitesimal endpoint motions of Line `e` under **shared topology and immutable datums but no Driving constraints**.
- Let `C_e` be the corresponding endpoint-motion space under all supported Driving constraints, obtained by projecting the global/component null space onto the Line's endpoint coordinates.
- **FREE:** `C_e = M_e`; no Driving constraint reduces any attainable motion of this Line. A constraint elsewhere or even incident to a shared point does not darken the Line if its attainable endpoint-motion space is unchanged.
- **CONSTRAINED:** `0 < dim(C_e) < dim(M_e)`, or more generally `C_e` is a proper nonzero subspace of `M_e`. At least one Line endpoint/shape/pose motion has been removed, but some Line motion remains.
- **FULLY CONSTRAINED:** `dim(C_e)=0`; neither endpoint has any admissible infinitesimal motion relative to immutable datums. This is stronger and more useful than “length/orientation fixed”: a rigid Line that can globally translate is not fully constrained.

For robustness at singular configurations, equality/subspace rank tests must use the canonical numerical tolerance and can be supplemented by finite perturbation checks. Presentation may optionally expose separate glyphs for fixed length/orientation rather than overloading the three colors.

General consequences:

- isolated length: constrained, with translation and rotation remaining;
- horizontal/vertical **distance**: constrained, with orthogonal relative motion and translation remaining;
- aligned/point-to-point: constrained for every Line whose attainable endpoint space is genuinely reduced;
- point-to-line and line-to-line: all participating Lines are evaluated by their own projected motion spaces, not colored en masse;
- shared neighbor: free if the equation does not reduce its attainable endpoint-motion space; constrained if coupling at the shared point truly removes a motion;
- Origin/fixed datum: no datum variables; enough independent restrictions can drive projected entity mobility to zero;
- future angle/Parallel/Perpendicular/H/V/Coincident/Fixed: each contributes differentiable equation rows (two rows for Coincident/Fixed point), and the same projected-space definition applies.

A subtle result is that BC in `A-B-C, |AB|=L` can reasonably remain FREE under this counterfactual definition: without and with the equation, any desired infinitesimal `(dB,dC)` can still be realized because `dA` can respond to satisfy the one scalar equation. AB is CONSTRAINED because its radial relative endpoint motion is removed.

## RECOMMENDED DRAG SEMANTICS

A partial constraint removes only forbidden components:

1. Treat pointer position/delta as a temporary soft or weighted edit objective on the selected point(s), not an unconditional coordinate replacement.
2. Solve all supported Driving equations in the affected equation component.
3. Preserve explicit immutable datums and Fixed constraints exactly.
4. Use stays/regularization to minimize movement of unselected points and preserve the user's ownership expectation while allowing them to respond where necessary.
5. For a Line drag, target equal endpoint displacement (rigid translation intent) but permit the constrained solution to project/couple as policy dictates.
6. Verify residuals and reject only if the system is inconsistent, degenerate, or the target has zero attainable projection.
7. Keep one preview session based on the drag-start snapshot and commit exactly one atomic History transaction on pointer-up.

For true zero entity mobility, point and Line drags remain rejected unless the interaction explicitly edits a constraint. A horizontal geometric constraint would enforce `dBy-dAy=0` while allowing translation and length change; a fixed point would have `dA=0` while other points retain their available modes.

## FUTURE CONSTRAINT COMPATIBILITY

- **Horizontal/Vertical geometric:** one orientation row, distinct from horizontal/vertical dimensional distance.
- **Parallel/Perpendicular:** one angular relationship row between Lines; global pose modes remain.
- **Coincident:** two scalar rows equating x and y unless canonical shared-point topology eliminates those duplicate variables instead.
- **Fixed point:** eliminate two variables or add two datum rows.
- **Angle:** one angular row, with degeneracy handling for zero-length Lines.

The observable null-space definition is independent of constraint labels. Reference dimensions must remain measurement-only and never enter `J`, visual restriction attribution, or drag preservation equations. Current supported analysis respects this, except the existing angle type has no equation and therefore needs an explicit future implementation before it can participate consistently.

## PERFORMANCE

- **Full Jacobian per Line:** simple but `O(number of Lines × factorization cost)` and unsuitable for pointer-rate work.
- **Cached component factorization/null space:** preferred. Build once per sketch revision/constraint topology/linearization point, then project each Line's four endpoint rows into the cached basis. Invalidate on point movement because nonlinear Jacobians change; topology-only incidence maps can survive coordinate-only changes.
- **Rank tests:** useful for classification but repeated remove-one-constraint counterfactual tests are expensive. Rank-revealing QR/SVD with updates is safer than bespoke elimination for near-dependence.
- **Null-space reuse:** one component basis serves point mobility, Line observables, zero-DOF gating, and first-order drag projection. Do not reuse it as the entire finite nonlinear solver.
- **Local incidence heuristics:** retain for fast dirty-component discovery and preliminary FREE candidates, but confirm semantic state with projected rank when a relevant Driving equation exists.

At drag rate, factor/relinearize only the affected equation component, warm-start from the last preview, and keep rendering/History outside analysis internals.

## RISK ANALYSIS

- Coloring every incident entity constrained preserves a simple test but misleads users; changing to mere “any mobility” would instead incorrectly label fixed-length Lines FREE. Baseline-vs-constrained projected spaces are necessary.
- Treating topological connectivity as equations would subtract DOF twice because shared SketchPoints already encode coincidence by common variables.
- A component-level zero DOF is not automatically entity zero DOF if “component” construction omits topological relations or splits endpoint components; entity projection must be authoritative.
- Naively moving the entire Line-topology component during drag can disturb unrelated geometry and recreate the pre-D2.5b4b “poison” problem.
- Hard anchoring every nonselected point reproduces current freeze; no stays permits arbitrary solver drift. Objective weights and deterministic tie-breaking need tests.
- Linear null-space projection alone accumulates constraint error on finite nonlinear drags. Re-solve and verify each preview.
